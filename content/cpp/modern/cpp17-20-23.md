# C++17, C++20 và C++23: Những thay đổi quan trọng

C++ là ngôn ngữ liên tục phát triển. Những phiên bản mới không chỉ bổ sung cú pháp mà còn cải tiến hệ thống kiểu, cách tổ chức chương trình, khả năng lập trình tổng quát và thư viện chuẩn.

Trong số các phiên bản Modern C++, ba cột mốc đáng chú ý là:

- **C++17:** Hoàn thiện nhiều công cụ nền tảng, bổ sung các tiện ích thư viện và cải thiện cách viết chương trình.
- **C++20:** Một bản nâng cấp lớn với Concepts, Ranges, Coroutines, Modules và những thay đổi quan trọng trong ngôn ngữ.
- **C++23:** Tiếp tục cải tiến tính biểu đạt, khả năng xử lý lỗi, lập trình tổng quát và thư viện chuẩn.

Tuy nhiên, phiên bản mới hơn không tự động đồng nghĩa với chương trình nhanh hơn, an toàn hơn hoặc dễ bảo trì hơn.

Việc lựa chọn chuẩn C++ cần dựa trên **những tính năng thực sự cần thiết, khả năng hỗ trợ của toolchain và yêu cầu tương thích của dự án**.

Bài viết này tập trung vào:

1. Những thay đổi quan trọng giữa C++17, C++20 và C++23.
2. Ví dụ thực tế của các tính năng mới.
3. Sự khác biệt giữa hỗ trợ ngôn ngữ và thư viện chuẩn.
4. Cách kiểm tra tính năng bằng feature-test macros.
5. Cấu hình GCC, Clang, MSVC và CMake.
6. Những rủi ro khi nâng cấp dự án.
7. Chiến lược lựa chọn và duy trì chuẩn C++ lâu dài.

**Đối tượng:** Người học đã nắm được C++ căn bản, hàm, reference, pointer, class và những container thường dùng.

## 1. Hiểu đúng về các phiên bản C++

### 1.1. Phiên bản C++ là gì?

Mỗi phiên bản C++ là một lần cập nhật tiêu chuẩn ngôn ngữ và thư viện chuẩn do tổ chức tiêu chuẩn hóa quốc tế công bố.

Một phiên bản có thể thay đổi:

- Cú pháp và quy tắc ngôn ngữ.
- Cách kiểm tra kiểu.
- Các công cụ lập trình tổng quát.
- Quy tắc về đối tượng và biểu thức.
- Những thành phần của Standard Library.
- Một số hành vi được tiêu chuẩn quy định.

Ví dụ, đoạn mã:

```cpp
auto [name, score] = student;
```

sử dụng *structured bindings*, được giới thiệu trong C++17.

Trong khi đó:

```cpp
template <std::integral T>
T square(T value) {
    return value * value;
}
```

sử dụng Concepts của C++20 và cần include `<concepts>`.

Vì vậy, một chương trình hợp lệ trong C++20 chưa chắc biên dịch được bằng chế độ C++17.

### 1.2. Chuẩn mới có thay thế hoàn toàn chuẩn cũ?

Không.

Phần lớn những kiến thức cơ bản như biến, hàm, vòng lặp, class và thuật toán vẫn tiếp tục được sử dụng.

Ví dụ:

```cpp
for (int i = 0; i < 10; ++i) {
    std::cout << i << '\n';
}
```

vẫn hợp lệ trong C++17, C++20 và C++23.

Tuy nhiên, không nên hiểu các phiên bản mới luôn tương thích hoàn toàn với mã cũ.

Một số thay đổi có thể khiến chương trình trước đây biên dịch được nhưng không còn hợp lệ, hoặc thay đổi cách compiler diễn giải một biểu thức.

Đó là lý do nâng chuẩn cần được xem như một thay đổi kỹ thuật có thể ảnh hưởng đến toàn bộ dự án.

## 3. C++17: Nền tảng Modern C++

C++17 được phát hành trong chu kỳ tiêu chuẩn năm 2017.

Phiên bản này tập trung cải thiện tính rõ ràng, giảm mã lặp và bổ sung những công cụ thư viện phổ biến.

### 3.1. Structured bindings

Trước C++17, khi sử dụng `std::pair`, chúng ta thường truy cập:

```cpp
point.first;
point.second;
```

C++17 cho phép tách các thành phần và đặt tên bằng structured bindings.

```cpp
#include <iostream>
#include <utility>

int main() {
    std::pair<int, int> point{10, 20};

    auto [x, y] = point;

    std::cout << x << ' ' << y << '\n';
}
```

Kết quả:

```text
10 20
```

Structured bindings còn hữu ích khi duyệt map:

```cpp
for (const auto& [name, score] : scores) {
    std::cout << name << ": " << score << '\n';
}
```

Thay vì:

```cpp
for (const auto& entry : scores) {
    std::cout << entry.first << ": "
              << entry.second << '\n';
}
```

Cách viết mới thường dễ đọc hơn khi các thành phần có ý nghĩa riêng.

### 3.2. if constexpr

`if constexpr` cho phép lựa chọn nhánh tại thời điểm biên dịch dựa trên biểu thức hằng.

Ví dụ:

```cpp
#include <iostream>
#include <type_traits>

template <typename T>
void describe(const T& value) {
    if constexpr (std::is_integral_v<T>) {
        std::cout << "Integer: " << value << '\n';
    } else {
        std::cout << "Other type\n";
    }
}

int main() {
    describe(42);
    describe(3.14);
}
```

Kết quả:

```text
Integer: 42
Other type
```

Khác với `if` thông thường, trong ngữ cảnh template phù hợp, nhánh không được chọn sẽ bị loại bỏ sau khi điều kiện được xác định khi khởi tạo template.

Điều này giúp viết generic code mà không cần dùng quá nhiều kỹ thuật SFINAE phức tạp.

### 3.3. std::optional

`std::optional<T>` biểu diễn một giá trị có thể tồn tại hoặc không tồn tại.

Header:

```cpp
#include <optional>
```

Ví dụ:

```cpp
#include <iostream>
#include <optional>

std::optional<int> findPositive(int value) {
    if (value <= 0) {
        return std::nullopt;
    }

    return value;
}

int main() {
    auto result = findPositive(10);

    if (result.has_value()) {
        std::cout << *result << '\n';
    }
}
```

Kết quả:

```text
10
```

`std::optional` giúp tránh sử dụng những giá trị đặc biệt như `-1` để biểu diễn thất bại khi `-1` cũng có thể là một giá trị hợp lệ của dữ liệu.

Tuy nhiên, optional không chứa thông tin chi tiết về nguyên nhân thất bại. Đây là một khác biệt quan trọng so với `std::expected` của C++23.

### 3.4. std::variant

`std::variant` có thể lưu một giá trị thuộc một trong nhiều kiểu được khai báo trước.

```cpp
#include <iostream>
#include <string>
#include <variant>

int main() {
    std::variant<int, std::string> value{42};

    std::cout << std::get<int>(value) << '\n';

    value = std::string{"Hello"};

    std::cout << std::get<std::string>(value) << '\n';
}
```

Kết quả:

```text
42
Hello
```

`std::variant` là một dạng type-safe discriminated union, phù hợp với dữ liệu có nhiều trạng thái được xác định rõ.

### 3.5. Những bổ sung khác của C++17

| Tính năng | Vai trò |
|---|---|
| `std::string_view` | Biểu diễn vùng dữ liệu chuỗi không sở hữu |
| `std::filesystem` | Thao tác với đường dẫn và hệ thống tệp |
| `std::any` | Lưu giá trị thuộc nhiều kiểu khác nhau |
| Inline variables | Cho phép định nghĩa biến inline phù hợp trong header |
| Class template argument deduction | Suy luận tham số template khi khởi tạo đối tượng |
| Fold expressions | Xử lý parameter packs trong template |

**Giới hạn cần hiểu:** Những kiểu không sở hữu dữ liệu như `std::string_view` không tự bảo đảm vùng dữ liệu tham chiếu vẫn còn sống.

C++17 cung cấp công cụ hiện đại hơn, nhưng người lập trình vẫn phải hiểu lifetime và ownership.

## 4. C++20: Một bước nâng cấp lớn

C++20 được xem là một trong những phiên bản quan trọng nhất kể từ C++11.

Bốn nhóm tính năng nổi bật gồm:

- Concepts.
- Ranges.
- Coroutines.
- Modules.

Ngoài ra còn có nhiều cải tiến về compile-time programming, so sánh đối tượng, xử lý chuỗi và lập trình đồng thời.

---

## 5. Concepts trong C++20

### 5.1. Vấn đề của template truyền thống

Trong C++17, chúng ta có thể viết:

```cpp
template <typename T>
T add(T a, T b) {
    return a + b;
}
```

Tuy nhiên, không phải kiểu `T` nào cũng hỗ trợ toán tử `+`.

Nếu truyền một kiểu không phù hợp, compiler có thể tạo ra thông báo lỗi template khá dài.

### 5.2. Giải pháp với Concepts

C++20 cho phép định nghĩa các ràng buộc rõ ràng hơn.

Ví dụ:

```cpp
#include <concepts>
#include <iostream>

template <std::integral T>
T add(T a, T b) {
    return a + b;
}

int main() {
    std::cout << add(5, 3) << '\n';
}
```

Kết quả:

```text
8
```

Concept `std::integral` yêu cầu kiểu dữ liệu thỏa mãn ràng buộc kiểu số nguyên tương ứng.

Vì vậy, lời gọi:

```cpp
add(3.5, 2.5);
```

không thỏa ràng buộc của template trên.

Compiler có thể chẩn đoán trực tiếp vấn đề về ràng buộc kiểu.

### 5.3. Tự định nghĩa concept

```cpp
#include <concepts>

template <typename T>
concept Number =
    std::integral<T> || std::floating_point<T>;

template <Number T>
T square(T value) {
    return value * value;
}
```

Concept `Number` cho phép các kiểu thỏa mãn `std::integral` hoặc `std::floating_point`.

Đây là một cách mô tả hợp đồng kiểu tại compile time.

### 5.4. Khi nào nên sử dụng Concepts?

Concepts đặc biệt hữu ích khi:

- Xây dựng generic libraries.
- Thiết kế template APIs.
- Muốn mô tả ràng buộc kiểu rõ ràng.
- Cần cải thiện khả năng chẩn đoán lỗi template.
- Muốn giảm một phần độ phức tạp của SFINAE.

Tuy nhiên, Concepts không bảo đảm template luôn đúng về logic.

Một kiểu có thể thỏa mãn các ràng buộc cú pháp nhưng vẫn có hành vi không đáp ứng những giả định ngữ nghĩa của thuật toán.

**Khuyến nghị:** Chỉ áp dụng Concepts khi ràng buộc kiểu mang lại giá trị thực tế. Đừng biến mọi hàm thông thường thành template chỉ để sử dụng tính năng mới.

## 6. Ranges trong C++20

Ranges cải tiến cách làm việc với container, iterator và các phép biến đổi dữ liệu.

### 6.1. Cách làm với C++17

Giả sử có một vector số nguyên và cần in bình phương của các số chẵn.

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> numbers{1, 2, 3, 4, 5, 6};

    for (int value : numbers) {
        if (value % 2 == 0) {
            std::cout << value * value << ' ';
        }
    }

    std::cout << '\n';
}
```

Kết quả:

```text
4 16 36
```

Cách này hoàn toàn hợp lệ và dễ hiểu.

### 6.2. Cách làm với C++20 Ranges

```cpp
#include <iostream>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> numbers{1, 2, 3, 4, 5, 6};

    auto result =
        numbers
        | std::views::filter([](int x) {
            return x % 2 == 0;
        })
        | std::views::transform([](int x) {
            return x * x;
        });

    for (int value : result) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}
```

Kết quả:

```text
4 16 36
```

### 6.3. Ranges hoạt động như thế nào?

Trong ví dụ:

```cpp
std::views::filter(...)
```

tạo một view dùng để lựa chọn các phần tử thỏa điều kiện.

Còn:

```cpp
std::views::transform(...)
```

tạo một view biểu diễn kết quả của phép biến đổi.

Các view này thường hỗ trợ tính toán lười (*lazy evaluation*).

Điều đó có nghĩa những giá trị được xử lý khi chương trình thực sự duyệt view, thay vì nhất thiết tạo ra toàn bộ một vector kết quả ngay lập tức.

### 6.4. View không đồng nghĩa với container sở hữu dữ liệu

View là một range nhẹ được dùng để biểu diễn hoặc kết hợp cách duyệt dữ liệu. Khi tạo `filter_view` hoặc `transform_view` từ một lvalue container như `numbers`, range bên trong thường là `std::ranges::ref_view` và chỉ quan sát container đó. Với một rvalue range, view pipeline có thể giữ dữ liệu bằng `std::ranges::owning_view`. Vì vậy, không nên kết luận rằng mọi view đều sở hữu dữ liệu hoặc rằng mọi view đều không sở hữu dữ liệu.

Ví dụ:

```cpp
auto even = numbers | std::views::filter(predicate);
```

Trong biểu thức trên, `numbers` là lvalue còn sống bên ngoài view, nên view phụ thuộc vào lifetime của `numbers`. Nếu source bị hủy, hoặc thao tác trên source làm iterator của view mất hiệu lực, không được tiếp tục dùng view như thể nó vẫn trỏ tới dữ liệu hợp lệ.

Khi lưu view qua một hàm hoặc trả nó khỏi hàm, cần xác định view cụ thể có sở hữu range hay chỉ quan sát nó. Đọc điều kiện lifetime của adaptor đang dùng; đừng suy ra ownership chỉ từ tên `view`.

**Cần phân biệt:**

- Container: Quản lý một tập hợp dữ liệu theo hợp đồng của nó.
- Range: Khái niệm tổng quát về một dãy có thể duyệt.
- View: Một loại range phù hợp để xây dựng các thao tác và phép biến đổi, không nhất thiết sở hữu dữ liệu.

### 6.5. Khi nào nên dùng Ranges?

Ranges phù hợp khi chương trình có nhiều bước:

- Lọc dữ liệu.
- Biến đổi dữ liệu.
- Lấy một phần dãy.
- Kết hợp các phép xử lý.
- Làm việc với generic algorithms.

Tuy nhiên, một vòng lặp `for` đơn giản vẫn có thể dễ đọc hơn một pipeline phức tạp.

Độ ngắn của mã nguồn không phải tiêu chí duy nhất để đánh giá khả năng bảo trì.

## 7. std::span trong C++20

`std::span` cung cấp một view không sở hữu trên một dãy phần tử liên tiếp trong bộ nhớ.

Header:

```cpp
#include <span>
```

### 7.1. Ví dụ

```cpp
#include <array>
#include <iostream>
#include <span>
#include <vector>

void printValues(std::span<const int> values) {
    for (int value : values) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}

int main() {
    std::array<int, 3> fixed{1, 2, 3};
    std::vector<int> dynamic{4, 5, 6};

    printValues(fixed);
    printValues(dynamic);
}
```

Kết quả:

```text
1 2 3
4 5 6
```

### 7.2. Lợi ích

Trong C++17, một API có thể phải nhận:

```cpp
void process(const int* data, std::size_t size);
```

Với C++20:

```cpp
void process(std::span<const int> data);
```

`std::span` kết hợp thông tin về vùng phần tử và kích thước trong cùng một đối tượng.

Nó giúp giao diện rõ ràng hơn và giảm nguy cơ truyền sai số phần tử.

Tuy nhiên:

- `std::span` không sở hữu vùng nhớ.
- Không tự kéo dài lifetime của dữ liệu nguồn.
- Không biến mọi truy cập ngoài biên thành exception.
- Có thể mất hiệu lực nếu vùng lưu trữ nguồn không còn hợp lệ.

**Nguyên tắc:** `std::span` là công cụ biểu diễn một vùng dữ liệu liên tiếp, không phải công cụ quản lý quyền sở hữu.

## 8. Coroutines trong C++20

Coroutines cho phép một hàm tạm dừng thực thi và tiếp tục sau đó mà không cần kết thúc hoàn toàn trạng thái thực thi của nó.

Chúng hữu ích trong những hệ thống như:

- Asynchronous I/O.
- Event-driven programming.
- Generators.
- Task scheduling.
- Các framework xử lý bất đồng bộ.

C++20 giới thiệu những cơ chế ngôn ngữ:

```cpp
co_await
co_yield
co_return
```

### 8.1. Coroutines không đồng nghĩa với đa luồng

Đây là một nhầm lẫn phổ biến.

Coroutine không tự động tạo thread mới.

Nó cũng không tự biến mọi hàm thành thao tác bất đồng bộ.

Cơ chế tạm dừng, tiếp tục thực thi và lập lịch phụ thuộc vào coroutine type, awaiter và framework sử dụng.

### 8.2. Coroutine cần hạ tầng phù hợp

C++20 cung cấp các cơ chế cốt lõi và header `<coroutine>`, nhưng không cung cấp một coroutine task framework tổng quát để thay thế mọi thư viện bất đồng bộ.

Việc tự xây dựng coroutine type cần hiểu:

- Coroutine promise.
- Coroutine handle.
- Suspension points.
- Lifetime của coroutine frame.
- Quy tắc hủy và tiếp tục thực thi.

Đó là lý do nên học Coroutines trong một bài chuyên sâu, thay vì sử dụng chúng chỉ để thay thế hàm hoặc vòng lặp thông thường.

## 9. Modules trong C++20

Modules được thiết kế nhằm cải tiến mô hình tổ chức mã nguồn và những vấn đề liên quan đến header truyền thống.

### 9.1. Cách tổ chức truyền thống

C++ thường sử dụng:

```cpp
#include "Math.h"
```

Header được đưa vào quá trình tiền xử lý, thường làm cho nhiều translation unit phải phân tích lại những nội dung giống nhau.

Với dự án lớn, điều này có thể làm tăng chi phí build.

### 9.2. Module interface

Ví dụ một module đơn giản:

```cpp
export module Math;

export int add(int a, int b) {
    return a + b;
}
```

Trong một translation unit khác:

```cpp
import Math;

int main() {
    return add(2, 3);
}
```

Đây là ví dụ cú pháp C++20.

**Lưu ý:** Không thể giả định chỉ cần đưa hai đoạn mã vào hai file `.cpp` rồi gọi lệnh biên dịch thông thường là mọi compiler đều xử lý modules chính xác.

Quá trình build phải cung cấp dependency ordering và quản lý những sản phẩm trung gian của module theo yêu cầu toolchain.

### 9.3. Modules có thay thế hoàn toàn headers?

Không nhất thiết.

Trong thực tế, nhiều dự án vẫn sử dụng:

- Traditional headers.
- Header-only libraries.
- Modules.
- Các thư viện bên thứ ba chưa hỗ trợ modules.

Modules và headers có thể cùng tồn tại trong một dự án.

### 9.4. Khi nào nên áp dụng Modules?

Modules đáng cân nhắc khi:

- Dự án có quy mô đủ lớn.
- Toolchain được kiểm soát.
- Build system hỗ trợ module dependency scanning.
- Các dependency cần thiết tương thích.
- Đội ngũ hiểu những vấn đề tích hợp và build cache.

Không nên chuyển toàn bộ framework sang Modules chỉ vì đang nâng từ C++17 lên C++20.

**Trade-off:** Modules có thể cải thiện cách tổ chức và hiệu quả build, nhưng cũng bổ sung yêu cầu mới đối với compiler, build system và quản lý dependency.

## 10. Những cải tiến C++20 khác

Ngoài bốn nhóm tính năng lớn, C++20 còn bổ sung nhiều công cụ quan trọng.

### 10.1. Three-way comparison

Toán tử:

```cpp
<=>
```

được gọi là *three-way comparison operator*, hay spaceship operator.

Ví dụ:

```cpp
#include <compare>

struct Version {
    int major{};
    int minor{};

    auto operator<=>(const Version&) const = default;
};
```

Với các thành viên phù hợp, compiler có thể sinh phép so sánh theo thứ tự khai báo các thành viên.

Điều này giúp giảm mã lặp khi định nghĩa quan hệ thứ tự cho một kiểu dữ liệu.

### 10.2. Designated initializers

```cpp
struct Config {
    int width{};
    int height{};
};

Config config{
    .width = 1920,
    .height = 1080
};
```

C++20 hỗ trợ designated initializers cho những aggregate phù hợp.

Lưu ý khác với C, C++ yêu cầu các designator tuân theo thứ tự khai báo thành viên.

### 10.3. std::format

Header:

```cpp
#include <format>
```

Ví dụ:

```cpp
#include <format>
#include <iostream>

int main() {
    const auto message =
        std::format("Score: {}", 95);

    std::cout << message << '\n';
}
```

Kết quả:

```text
Score: 95
```

`std::format` cung cấp cơ chế định dạng chuỗi hiện đại.

Tuy nhiên, nó là một tính năng thư viện. Mức hỗ trợ phụ thuộc vào standard library, không chỉ compiler.

### 10.4. std::jthread

`std::jthread` bổ sung một cơ chế quản lý thread thuận tiện hơn trong nhiều tình huống. Khi đối tượng còn joinable bị hủy, destructor yêu cầu dừng rồi join thread.

Yêu cầu dừng là cooperative cancellation: thread chỉ kết thúc sớm nếu công việc của nó nhận hoặc truy cập stop token và chủ động kiểm tra yêu cầu dừng. Destructor vẫn phải đợi thread kết thúc, nên một worker bỏ qua stop token có thể làm scope đóng chậm hoặc bị chặn lâu.

Điều này giảm một số lỗi quản lý vòng đời thread, nhưng không tự giải quyết data race, deadlock hoặc mọi vấn đề đồng bộ. Mọi truy cập dữ liệu dùng chung vẫn cần đồng bộ phù hợp.

## 11. C++23: Tập trung cải tiến khả năng sử dụng

C++23 tiếp tục mở rộng C++ với nhiều tiện ích mới.

Một số tính năng đáng chú ý:

| Tính năng | Mục đích |
|---|---|
| `std::expected` | Biểu diễn kết quả hoặc thông tin lỗi |
| `std::print` | Xuất dữ liệu có định dạng |
| `std::println` | Xuất dữ liệu có định dạng và xuống dòng |

| `std::ranges::to` | Chuyển range thành container |

| `if consteval` | Phân biệt ngữ cảnh đánh giá tại compile time |

## 12. std::expected trong C++23

`std::expected<T, E>` biểu diễn một kết quả có thể là:

- Giá trị thành công thuộc kiểu `T`.
- Thông tin lỗi thuộc kiểu `E`.

Đây là một công cụ hữu ích khi thiết kế API có khả năng thất bại theo những điều kiện thông thường.

### 12.1. So sánh với std::optional

Trong C++17:

```cpp
std::optional<int>
```

cho biết có hoặc không có một giá trị `int`.

Trong C++23:

```cpp
std::expected<int, std::string>
```

có thể biểu diễn giá trị `int` hoặc một chuỗi mô tả lỗi.

### 12.2. Ví dụ hoàn chỉnh

```cpp
#include <expected>
#include <iostream>
#include <string>

std::expected<int, std::string> divide(
    int a,
    int b
) {
    if (b == 0) {
        return std::unexpected(
            std::string{"Division by zero"}
        );
    }

    return a / b;
}

int main() {
    auto result = divide(10, 2);

    if (result.has_value()) {
        std::cout << *result << '\n';
    } else {
        std::cerr << result.error() << '\n';
    }
}
```

Kết quả:

```text
5
```

Nếu gọi:

```cpp
divide(10, 0);
```

hàm trả về thông tin lỗi thay vì thực hiện phép chia.

### 12.3. Vì sao expected hữu ích?

Một API có thể trả về nhiều nguyên nhân thất bại khác nhau.

Ví dụ:

- Dữ liệu đầu vào không hợp lệ.
- Không tìm thấy tài nguyên.
- Người dùng không có quyền.
- Kết nối đến dịch vụ thất bại.

`std::expected` giúp mô tả kết quả và lỗi trực tiếp trong kiểu trả về.

Tuy nhiên, nó không phải công cụ thay thế exception trong mọi trường hợp.

Cần lựa chọn cơ chế xử lý lỗi theo hợp đồng API, khả năng phục hồi và tính chất của lỗi.

**Lưu ý:** Hàm `divide()` ở trên là ví dụ minh họa cơ chế `expected`. Một API chia nguyên tổng quát còn cần xử lý các trường hợp tràn số có dấu như giá trị nhỏ nhất của `int` chia cho `-1`.

## 13. std::print và std::println

C++23 bổ sung các công cụ xuất dữ liệu định dạng trong header `<print>`.

### 13.1. Ví dụ

```cpp
#include <print>

int main() {
    std::print("Hello, {}!", "C++23");
    std::println();
    std::println("Score: {}", 95);
}
```

Kết quả:

```text
Hello, C++23!
Score: 95
```

### 13.2. So sánh với C++17

C++17:

```cpp
std::cout << "Score: " << score << '\n';
```

C++23:

```cpp
std::println("Score: {}", score);
```

`std::print` và `std::println` sử dụng cú pháp định dạng hiện đại, phù hợp khi xuất nhiều dữ liệu với định dạng cụ thể.

### 13.3. Hạn chế tương thích

`<print>` là một header C++23.

Một compiler có thể hỗ trợ cú pháp C++23 nhưng standard library đi kèm chưa có header này.

Khi đó chương trình vẫn biên dịch thất bại.

Nếu dự án cần hỗ trợ nhiều toolchain, nên kiểm tra tính năng và cung cấp phương án thay thế phù hợp.

## 14. std::mdspan và dữ liệu nhiều chiều

C++23 giới thiệu `std::mdspan`, một view cho dữ liệu nhiều chiều.

Nó đặc biệt hữu ích trong:

- Tính toán khoa học.
- Xử lý ma trận.
- Mô phỏng.
- Xử lý hình ảnh.
- Các hệ thống cần kiểm soát layout dữ liệu.

### 14.1. Ví dụ

```cpp
#include <array>
#include <iostream>
#include <mdspan>

int main() {
    std::array<int, 6> data{
        1, 2, 3,
        4, 5, 6
    };

    std::mdspan matrix(
        data.data(),
        2,
        3
    );

    std::cout << matrix[1, 2] << '\n';
}
```

Kết quả:

```text
6
```

Ví dụ sử dụng `std::mdspan` của C++23 cùng cú pháp truy cập nhiều chiều.

### 14.2. mdspan có sở hữu bộ nhớ không?

Không.

`std::mdspan` không tự sở hữu vùng dữ liệu mà nó quan sát.

Trong ví dụ trên, `std::array` sở hữu dữ liệu, còn `std::mdspan` cung cấp cách nhìn dữ liệu dưới dạng hai chiều.

Cần bảo đảm vùng nhớ nguồn còn sống và layout, extents phù hợp trong suốt thời gian sử dụng.

### 14.3. Khi nào nên sử dụng?

`std::mdspan` phù hợp nếu dự án đã có vùng dữ liệu liên tiếp và cần ánh xạ nó thành nhiều chiều mà không sao chép.

Nó không phải thay thế trực tiếp cho mọi cấu trúc ma trận có ownership.

Ngoài ra, mức hỗ trợ `<mdspan>` giữa các thư viện chuẩn có thể khác nhau.

## 15. Những cải tiến Ranges trong C++23

C++23 mở rộng Ranges với nhiều công cụ mới.

Một ví dụ là `std::ranges::to`, dùng để chuyển kết quả range thành container.

### 15.1. Ví dụ

```cpp
#include <iostream>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> numbers{1, 2, 3, 4, 5, 6};

    auto result =
        numbers
        | std::views::filter([](int x) {
            return x % 2 == 0;
        })
        | std::ranges::to<std::vector<int>>();

    for (int value : result) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}
```

Kết quả:

```text
2 4 6
```

Khác với một view chỉ biểu diễn quá trình duyệt, kết quả ở đây là một `std::vector<int>` sở hữu các phần tử được tạo ra.

### 15.2. Lựa chọn view hoặc container

Nên sử dụng view khi:

- Chỉ cần duyệt dữ liệu.
- Không cần lưu kết quả độc lập.
- Muốn kết hợp nhiều phép biến đổi.
- Lifetime của dữ liệu nguồn được quản lý rõ ràng.

Nên tạo container khi:

- Cần lưu kết quả lâu dài.
- Cần quyền sở hữu dữ liệu độc lập.
- Phải truyền kết quả đến những thành phần khác.
- Muốn tách kết quả khỏi những thay đổi của dữ liệu nguồn.

**Không nên biến mọi pipeline thành vector nếu chương trình chỉ cần duyệt một lần.**

Ngược lại, cũng không nên giữ một view không sở hữu dữ liệu khi nguồn có thể bị hủy trước thời điểm sử dụng.

## 16. Explicit object parameter trong C++23

C++23 bổ sung khả năng khai báo tường minh tham số đối tượng cho một số hàm thành viên, thường được gọi là *deducing this*.

Ví dụ:

```cpp
#include <iostream>

struct Counter {
    int value{};

    int get(this const Counter& self) {
        return self.value;
    }
};

int main() {
    Counter counter{42};

    std::cout << counter.get() << '\n';
}
```

Kết quả:

```text
42
```

Trong hàm:

```cpp
int get(this const Counter& self)
```

`self` là tham số đối tượng tường minh.

Cơ chế này có ứng dụng trong generic programming, forwarding và thiết kế các API cần thao tác linh hoạt với kiểu của đối tượng.

Tuy nhiên, nó không phải cú pháp bắt buộc để viết class trong C++23.

Đối với những hàm thành viên đơn giản, cú pháp truyền thống vẫn hoàn toàn phù hợp:

```cpp
int get() const {
    return value;
}
```

## 17. Kiểm tra compiler và standard library

Đây là một phần quan trọng khi sử dụng C++20 hoặc C++23 trong dự án thực tế.

### 17.1. Ba lớp hỗ trợ cần phân biệt

Không nên chỉ kiểm tra compiler có chấp nhận cờ chuẩn hay không.

Cần phân biệt:

| Thành phần | Câu hỏi |
|---|---|
| Language support | Compiler có hiểu cú pháp và quy tắc tính năng không? |
| Library support | Standard library có cung cấp header và API không? |
| Toolchain integration | Linker, build system và nền tảng đích có hỗ trợ không? |

Ví dụ:

Một compiler có thể hiểu cú pháp:

```cpp
template <std::integral T>
```

nhưng standard library cũ không có `<print>`.

Hoặc compiler hỗ trợ Modules, nhưng build system chưa được cấu hình để xử lý module dependency.

### 17.2. Kiểm tra phiên bản compiler

GCC:

```sh
g++ --version
```

Clang:

```sh
clang++ --version
```

MSVC, trong Developer Command Prompt:

```bat
cl
```

Những lệnh trên cho biết phiên bản compiler được sử dụng.

Tuy nhiên, số phiên bản compiler không phải bằng chứng đầy đủ về khả năng hỗ trợ từng tính năng.

### 17.3. Các nguồn kiểm tra chính thức

Sử dụng những bảng hỗ trợ sau:

- [GCC C++ Standards Support](https://gcc.gnu.org/projects/cxx-status.html)
- [Clang C++ Status](https://clang.llvm.org/cxx_status.html)
- [Microsoft C/C++ Language Conformance](https://learn.microsoft.com/en-us/cpp/visual-cpp-language-conformance)
- [cppreference Compiler Support](https://en.cppreference.com/w/cpp/compiler_support)

Khi kiểm tra một tính năng, cần xác định:

1. Phiên bản compiler bắt đầu hỗ trợ.
2. Tính năng đã được triển khai đầy đủ hay mới một phần.
3. Header và standard library có sẵn không.
4. Có yêu cầu cờ build riêng không.
5. Có giới hạn nền tảng hoặc vấn đề tương thích nào không.

### 17.4. Không hardcode số phiên bản compiler

Ví dụ, không nên chỉ dựa vào:

```cpp
#if __GNUC__ >= 12
```

để kết luận tất cả tính năng C++23 đều sẵn sàng.

Phiên bản compiler có thể không phản ánh đầy đủ phiên bản hoặc cấu hình standard library đang sử dụng.

Ngoài ra, các macro nhận dạng compiler đôi khi cũng được những compiler tương thích định nghĩa.

**Giải pháp tốt hơn:** Kiểm tra trực tiếp tính năng bằng feature-test macros hoặc compile tests.

## 18. Feature-test macros

C++ cung cấp các macro để kiểm tra mức hỗ trợ của nhiều tính năng ngôn ngữ và thư viện chuẩn.

### 18.1. Macro kiểm tra phiên bản ngôn ngữ

Ví dụ:

```cpp
#include <iostream>

int main() {
    std::cout << __cplusplus << '\n';
}
```

Các giá trị tiêu biểu:

| Phiên bản | Giá trị |
|---|---|
| C++17 | `201703L` |
| C++20 | `202002L` |
| C++23 | `202302L` |

Trong MSVC, có thể cần bật `/Zc:__cplusplus` để macro phản ánh đúng chế độ ngôn ngữ.

### 18.2. Kiểm tra tính năng ngôn ngữ

Ví dụ:

```cpp
#if defined(__cpp_concepts) && __cpp_concepts >= 202002L
    #define HAS_CONCEPTS 1
#else
    #define HAS_CONCEPTS 0
#endif
```

Macro `__cpp_concepts` cho biết mức hỗ trợ tương ứng của Concepts.

Cần lưu ý rằng các macro có thể có nhiều giá trị phiên bản khác nhau khi tiêu chuẩn hoặc các defect report làm thay đổi tính năng.

Vì vậy, kiểm tra ngưỡng phiên bản cần dựa trên đúng yêu cầu của code.

### 18.3. Kiểm tra tính năng thư viện

Các thư viện chuẩn cung cấp nhiều macro có tiền tố:

```cpp
__cpp_lib_
```

Ví dụ:

```cpp
__cpp_lib_expected
__cpp_lib_print
__cpp_lib_ranges
__cpp_lib_span
```

Trong C++20 trở lên, header `<version>` là một cách tiêu chuẩn để truy cập các library feature-test macros.

Ví dụ, trong mã yêu cầu tối thiểu C++20:

```cpp
#include <version>

#if defined(__cpp_lib_ranges)
    // Ranges library is advertised as supported
#endif
```

### 18.4. Kiểm tra std::expected

Ví dụ một dự án cần hỗ trợ C++20 và tận dụng `std::expected` khi có C++23:

```cpp
#if defined(__has_include)
    #if __has_include(<expected>)
        #include <expected>
    #endif
#endif

#if defined(__cpp_lib_expected) && \
    __cpp_lib_expected >= 202202L
    #define HAS_EXPECTED 1
#else
    #define HAS_EXPECTED 0
#endif
```

Sau đó:

```cpp
#if HAS_EXPECTED
    // C++23 implementation
#else
    // Compatible fallback
#endif
```

Header có tồn tại không đồng nghĩa tính năng đã được triển khai với đúng phiên bản cần sử dụng.

Vì thế cần kiểm tra macro sau khi include header phù hợp.

### 18.5. Compile tests

Feature-test macros rất hữu ích, nhưng không thay thế hoàn toàn việc biên dịch thử đoạn mã thực tế.

Một tính năng có thể gặp:

- Hỗ trợ chưa đầy đủ.
- Lỗi implementation.
- Giới hạn khi kết hợp với tính năng khác.
- Vấn đề ABI hoặc linking.
- Cấu hình build không phù hợp.

Với hệ thống production, nên kết hợp feature-test macros, compile tests và CI.

### 19.2. Clang

```

```

C++23:

```sh
clang++ -std=c++23 -Wall -Wextra -Wpedantic main.cpp -o app
```

Không nên sử dụng chế độ này làm mặc định cho một dự án production yêu cầu build ổn định và tái lập được.

**Lưu ý:** Các tùy chọn hỗ trợ C++23 của MSVC có thể thay đổi giữa những bản phát hành. Luôn kiểm tra tài liệu `/std` tương ứng với toolset đang sử dụng.

## 20. Quản lý chuẩn C++ bằng CMake

Trong dự án có nhiều source file và nhiều nền tảng, không nên phải truyền thủ công cờ `-std=` ở mọi nơi.

CMake cho phép mô tả yêu cầu chuẩn theo target.

### 20.1. Cấu hình C++17

```cmake
cmake_minimum_required(VERSION 3.20)

project(ModernCpp LANGUAGES CXX)

add_executable(app main.cpp)

set_target_properties(app PROPERTIES
    CXX_STANDARD 17
    CXX_STANDARD_REQUIRED YES
    CXX_EXTENSIONS NO
)
```

### 20.2. Cấu hình C++20

Thay:

```cmake
CXX_STANDARD 17
```

thành:

```cmake
CXX_STANDARD 20
```

### 20.3. Cấu hình C++23

```cmake
cmake_minimum_required(VERSION 3.20)

project(ModernCpp LANGUAGES CXX)

add_executable(app main.cpp)

set_target_properties(app PROPERTIES
    CXX_STANDARD 23
    CXX_STANDARD_REQUIRED YES
    CXX_EXTENSIONS NO
)
```

CMake 3.20 bổ sung khả năng khai báo giá trị `23` cho thuộc tính `CXX_STANDARD`.

### 20.4. Ý nghĩa các thuộc tính

| Thuộc tính | Vai trò |
|---|---|
| `CXX_STANDARD` | Phiên bản chuẩn được yêu cầu |
| `CXX_STANDARD_REQUIRED` | Không cho phép âm thầm hạ xuống chuẩn thấp hơn |
| `CXX_EXTENSIONS` | Kiểm soát compiler-specific language extensions |

Với:

```cmake
CXX_STANDARD_REQUIRED YES
```

CMake không được âm thầm chuyển yêu cầu C++23 thành C++20 chỉ vì toolchain thiếu khả năng chọn chuẩn tương ứng.

Tuy nhiên, cấu hình này không chứng minh mọi API C++23 đã được triển khai.

### 20.5. Khi nào dùng target_compile_features?

CMake cũng hỗ trợ:

```cmake
target_compile_features(app PRIVATE cxx_std_20)
```

Cách này diễn đạt yêu cầu tính năng chuẩn tối thiểu của target.

Tuy nhiên, với dự án cần kiểm soát nghiêm ngặt chế độ chuẩn và hạn chế extensions, nên thiết lập rõ các thuộc tính liên quan.

### 20.6. Không thay đổi chuẩn toàn bộ dự án nếu không cần thiết

Giả sử dự án gồm:

```text
Project/
├── core/
├── app/
└── tools/
```

Trong đó:

- `core` cần hỗ trợ C++17.
- `app` muốn sử dụng C++20.
- `tools` là công cụ nội bộ sử dụng C++23.

Có thể cân nhắc cấu hình riêng theo target nếu ranh giới API và dependency cho phép.

Không nên nâng yêu cầu chuẩn của toàn bộ thư viện công khai chỉ vì một công cụ nội bộ cần tính năng mới.

Tuy nhiên, cần kiểm tra rằng các target và thư viện được liên kết tương thích về compiler, ABI, runtime và những kiểu dữ liệu xuất hiện trong giao diện công khai.

## 21. Những thay đổi có thể ảnh hưởng mã nguồn cũ

Nâng chuẩn C++ không chỉ là thay đổi một cờ build.

Một số thay đổi giữa các phiên bản có thể ảnh hưởng đến source compatibility.

### 21.1. char8_t trong C++20

Trong C++17:

```cpp
const char* text = u8"Hello";
```

là cú pháp hợp lệ.

Trong C++20, UTF-8 string literal với tiền tố `u8` có kiểu mảng `const char8_t` thay vì mảng `const char`.

Vì vậy, đoạn gán trên không còn hợp lệ theo cùng cách.

Cách biểu diễn phù hợp với kiểu mới:

```cpp
const char8_t* text = u8"Hello";
```

Cần đặc biệt chú ý khi tích hợp với thư viện hoặc API vẫn yêu cầu `const char*`.

Không nên xử lý sự khác biệt bằng ép kiểu tùy tiện mà không xác định rõ encoding và hợp đồng API.

### 21.2. Thay đổi quy tắc so sánh

C++20 bổ sung three-way comparison và những thay đổi liên quan đến overload resolution của phép so sánh.

Một số kiểu có overload toán tử phức tạp có thể bị ảnh hưởng khi nâng chuẩn.

### 21.3. Thay đổi constexpr và template

Các phiên bản mới nới rộng khả năng compile-time programming.

Đồng thời, những thay đổi về language rules, constraints và defect reports có thể khiến một đoạn template trước đây hoạt động theo một cách nhưng được phân tích khác trong chuẩn mới.

### 21.4. Thay đổi standard library

Một số API có thể:

- Được bổ sung overload.
- Thay đổi ràng buộc template.
- Được đánh dấu deprecated.
- Được điều chỉnh do defect reports.
- Có yêu cầu hoặc hành vi được làm rõ.

Điều đó có thể tác động đến overload resolution, khả năng biên dịch hoặc tính tương thích của mã nguồn.

**Nguyên tắc:** Nâng chuẩn phải đi kèm kiểm tra thực tế, kể cả khi dự án không trực tiếp sử dụng tính năng mới.

## 22. Chiến lược nâng cấp C++17 lên C++20 hoặc C++23

Với dự án có nhiều module, nên nâng chuẩn theo từng giai đoạn.

### Giai đoạn 1. Kiểm tra toolchain

Xác định:

- Compiler đang sử dụng.
- Phiên bản standard library.
- Hệ điều hành và kiến trúc mục tiêu.
- Build system.
- Dependency.
- Những nền tảng cần hỗ trợ.

Không nâng chuẩn trước khi biết môi trường nào đang phụ thuộc vào phiên bản cũ.

### Giai đoạn 2. Nâng chuẩn mà chưa refactor

Ví dụ chuyển CMake từ:

```cmake
CXX_STANDARD 17
```

sang:

```cmake
CXX_STANDARD 20
```

Sau đó build lại dự án mà chưa thay đổi kiến trúc hoặc hàng loạt API.

Mục tiêu là xác định bản thân việc thay đổi chuẩn có gây lỗi hay không.

### Giai đoạn 3. Kiểm tra compiler warnings

Nên bật các cảnh báo phù hợp.

GCC/Clang:

```sh
-Wall -Wextra -Wpedantic
```

Nếu dự án có chính sách kiểm soát cảnh báo, có thể nâng dần yêu cầu thành warning-free build.

Không nên bật một tập hợp cảnh báo nghiêm ngặt rồi bỏ qua hàng trăm cảnh báo chưa được phân loại.

### Giai đoạn 4. Chạy kiểm thử

Cần chạy:

- Unit tests.
- Integration tests.
- Regression tests.
- Những bài kiểm thử liên quan đến lifetime.
- Những bài kiểm thử serialization hoặc binary compatibility khi có liên quan.
- Hiệu năng chuẩn nếu dự án nhạy cảm với performance.

Với GCC/Clang trên môi trường phù hợp, có thể sử dụng sanitizer:

```sh
g++ -std=c++20 -g -O1 \
    -fsanitize=address,undefined \
    -fno-omit-frame-pointer \
    main.cpp -o app
```

Sanitizer không chứng minh chương trình hoàn toàn an toàn, nhưng có thể phát hiện nhiều lỗi runtime quan trọng.

### Giai đoạn 5. Sử dụng tính năng mới có chọn lọc

Sau khi build và test ổn định, mới cân nhắc:

- Concepts cho generic APIs.
- Ranges cho data pipelines.
- `std::span` cho những API nhận vùng dữ liệu.
- `std::expected` cho các API xử lý lỗi phù hợp.
- Modules nếu build infrastructure sẵn sàng.

Không nên refactor toàn bộ codebase chỉ để thay thế những cấu trúc C++17 đang rõ ràng và hoạt động tốt.

## 23. Ba nhóm rủi ro cần đánh giá

### 23.1. Trường hợp thành công

Dự án nâng chuẩn, build thành công và kiểm thử đạt yêu cầu.

Những tính năng mới được sử dụng ở đúng vị trí, giúp giảm code lặp hoặc cải thiện thiết kế mà không làm tăng độ phức tạp không cần thiết.

### 23.2. Lỗi kỹ thuật hoặc tương thích

Các tình huống thường gặp:

- Compiler không hỗ trợ cú pháp.
- Standard library thiếu header.
- Linker không tìm thấy symbol.
- Build system không hỗ trợ Modules.
- Dependency không tương thích.
- ABI không tương thích giữa các thành phần.
- Mã nguồn bị ảnh hưởng bởi quy tắc chuẩn mới.

Cần xác định nguyên nhân thuộc lớp ngôn ngữ, thư viện, build system hay binary compatibility trước khi sửa.

### 23.3. Sử dụng sai hoặc lạm dụng tính năng mới

Ví dụ:

- Sử dụng Ranges pipeline phức tạp cho vòng lặp đơn giản.
- Giữ view sau khi dữ liệu nguồn hết lifetime.
- Dùng Coroutines nhưng không quản lý coroutine frame đúng cách.
- Áp dụng `std::shared_ptr` cho mọi đối tượng.
- Dùng Modules mà không kiểm soát build dependency.
- Bật `/std:c++latest` trong production nhưng không khóa phiên bản toolchain.

Tính năng mới không loại bỏ trách nhiệm thiết kế phần mềm.

Một số tính năng còn mang đến những quy tắc lifetime và dependency mới cần hiểu rõ.

## 24. Thiết kế CI cho nhiều phiên bản C++

Nếu một thư viện hoặc dự án cần hỗ trợ nhiều toolchain, nên xây dựng test matrix.

Ví dụ:

| Môi trường | Compiler | Chuẩn | Mục tiêu |
|---|---|---|---|
| Linux | GCC | C++17 | Kiểm tra baseline |
| Linux | GCC | C++20 | Kiểm tra nâng chuẩn |
| Linux | Clang | C++20 | Kiểm tra compiler khác |
| Windows | MSVC | C++17 | Tương thích Windows |
| Windows | MSVC | C++20 | Kiểm tra chuẩn hiện đại |
| Experimental | Toolchain được chọn | C++23 | Kiểm tra tính năng mới |

Đây là mô hình đề xuất, không phải cam kết mọi tổ hợp đều được hỗ trợ.

Trong CI thực tế, cần khóa phiên bản compiler và standard library tương ứng.

### 24.1. Đừng nhầm build matrix với feature matrix

**Build matrix** xác định những môi trường mà dự án thử nghiệm.

**Feature matrix** xác định những tính năng có thể sử dụng trong từng môi trường.

Ví dụ, hai toolchain cùng chạy C++23 nhưng có thể khác nhau về hỗ trợ `<print>` hoặc `<mdspan>`.

Do đó, một feature matrix có thể bao gồm:

```text
Feature           GCC    Clang    MSVC
--------------------------------------
Concepts          Test   Test     Test
Ranges            Test   Test     Test
std::expected     Test   Test     Test
std::print        Test   Test     Test
Modules           Test   Test     Test
```

Các ô `Test` có nghĩa cần chạy kiểm tra thực tế trên những phiên bản toolchain đã chọn, không phải khẳng định tính năng đang có hoặc không có.

### 24.2. Chính sách tương thích

Với thư viện công khai, nên công bố rõ:

- Minimum C++ standard.
- Supported compiler versions.
- Supported platforms.
- Required standard library features.
- Những tính năng tùy chọn.
- Các trường hợp không được hỗ trợ.

Không nên chỉ ghi chung chung:

```text
Requires Modern C++
```

Thông tin đó không đủ để người dùng xác định môi trường build phù hợp.

## 25. Lựa chọn chuẩn C++ theo dự án

| Loại dự án | Hướng lựa chọn |
|---|---|
| Học C++ căn bản | C++17 là baseline phù hợp |
| Luyện thuật toán | Theo chuẩn online judge |
| Ứng dụng desktop | C++17/20/23 tùy framework và toolchain |
| Thư viện phân phối rộng | Ưu tiên chuẩn tối thiểu đáp ứng yêu cầu |
| Generic library nâng cao | Cân nhắc C++20 Concepts |
| Data processing pipelines | Cân nhắc C++20 Ranges |
| Asynchronous framework | Cân nhắc Coroutines khi có hạ tầng phù hợp |
| API trả kết quả/lỗi | Cân nhắc C++23 `std::expected` |
| Công cụ nội bộ kiểm soát môi trường | Có thể nâng chuẩn nhanh hơn |
| Hệ thống nhúng | Theo hỗ trợ thực tế của target toolchain |

### 25.1. Có nên luôn chọn chuẩn mới nhất?

Không nhất thiết.

Ví dụ, nếu dự án hoạt động ổn định trên C++17 và không cần tính năng mới, nâng lên C++23 có thể không mang lại lợi ích tương xứng với chi phí.

Ngược lại, nếu phát triển generic libraries phức tạp, Concepts trong C++20 có thể giúp cải thiện API đáng kể.

Điều quan trọng không phải sử dụng phiên bản cao nhất mà là **chọn chuẩn đáp ứng nhu cầu với chi phí tương thích hợp lý**.

### 25.2. Có nên giữ mã C++17 nhưng biên dịch bằng C++23?

Có thể, nếu mã vẫn hợp lệ và toolchain hỗ trợ.

Tuy nhiên, cần hiểu rằng chế độ ngôn ngữ có thể ảnh hưởng đến quy tắc phân tích chương trình ngay cả khi bạn chưa sử dụng API mới.

Vì vậy, việc nâng mode vẫn cần được kiểm thử.

### 25.3. Khi nào nên nâng chuẩn toàn bộ dự án?

Nên cân nhắc khi:

- Có tính năng mới giải quyết được vấn đề kỹ thuật cụ thể.
- Các nền tảng mục tiêu đều hỗ trợ.
- Dependency tương thích.
- CI có thể kiểm tra đầy đủ.
- Đội ngũ có đủ kiến thức để bảo trì code mới.
- Chi phí nâng cấp được đánh giá và chấp nhận.

Nếu chỉ một module cần tính năng mới, có thể cân nhắc tách ranh giới phù hợp thay vì nâng toàn bộ codebase.

Tuy nhiên, nếu các module chia sẻ nhiều template hoặc API phụ thuộc tính năng mới, việc duy trì nhiều chuẩn trong một dự án có thể làm tăng độ phức tạp.

## 26. Những lỗi thường gặp

### 26.1. Bật C++23 nhưng thiếu header

Ví dụ:

```cpp
#include <print>
```

bị lỗi vì standard library chưa triển khai `<print>`.

Cần kiểm tra phiên bản standard library và tính năng cụ thể, không chỉ thay cờ compiler.

### 26.2. Sử dụng cờ compiler không được hỗ trợ

Không mặc định tất cả compiler đều có cùng tên tùy chọn.

GCC và Clang thường sử dụng:

```sh
-std=c++23
```

MSVC có hệ thống tùy chọn `/std:` riêng.

### 26.3. Sử dụng GNU extensions

Ví dụ, Variable Length Arrays không phải tính năng chuẩn của C++17, C++20 hoặc C++23.

Một compiler có thể chấp nhận chúng trong chế độ GNU extension.

Muốn kiểm tra tính portable, nên dùng chế độ chuẩn nghiêm ngặt và cảnh báo phù hợp.

### 26.4. Dùng Ranges nhưng bỏ qua lifetime

View có thể tham chiếu dữ liệu nguồn.

Nếu dữ liệu nguồn bị hủy hoặc thay đổi làm mất hiệu lực các iterator, việc sử dụng view có thể không còn an toàn.

### 26.5. Nâng chuẩn nhưng không kiểm tra dependency

Một số thư viện hoặc framework có thể có giới hạn phiên bản compiler, ABI hoặc standard library.

Không nên giả định rằng chỉ cần sửa `CXX_STANDARD` là toàn bộ dependency sẽ tương thích.

### 26.6. Dùng latest trong production

`/std:c++latest` hoặc các chế độ experimental có thể thay đổi tính năng được bật sau khi cập nhật compiler.

Dự án yêu cầu reproducible builds nên kiểm soát chặt phiên bản toolchain và lựa chọn chuẩn.

### 26.7. Refactor quá mức

Không cần đổi toàn bộ vòng lặp sang Ranges, toàn bộ header sang Modules hoặc toàn bộ hàm trả về sang `std::expected`.

Cần đánh giá từng thay đổi theo:

- Tính rõ ràng.
- Tính đúng đắn.
- Hiệu năng.
- Khả năng tương thích.
- Chi phí bảo trì.

## 27. Quy trình đưa tính năng mới vào dự án

Khi cân nhắc Concepts, Ranges, `std::span` hoặc `std::expected`, quyết định nên bắt đầu từ hợp đồng và môi trường của dự án:

1. **Chốt baseline và nền tảng cần hỗ trợ.** Ghi rõ chuẩn tối thiểu, compiler, standard library và hệ điều hành. Không coi một cờ `-std=` hoặc `/std:` là bằng chứng mọi API của chuẩn đó đã được cài đặt.
2. **Kiểm tra đúng tính năng.** Dùng feature-test macro sau khi include header phù hợp, rồi compile một đoạn sử dụng API thật. Header tồn tại nhưng thiếu một phần triển khai vẫn có thể khiến build thất bại.
3. **Đánh giá lifetime và ownership.** `std::span` và nhiều ranges views không kéo dài lifetime dữ liệu nguồn. `std::expected` biểu diễn lỗi trong kiểu trả về nhưng không tự xác định cách phục hồi hay exception policy.
4. **Đổi chuẩn trước, refactor sau.** Nâng target và build/test khi chưa thay hàng loạt API để tách lỗi do chế độ chuẩn khỏi lỗi do thay đổi mã.
5. **Đưa cấu hình vào CI.** Chạy build trên các toolchain được công bố hỗ trợ; tính năng tùy chọn như `std::print` cần compile test riêng nếu thư viện công khai phụ thuộc vào nó.
6. **Công bố chính sách tương thích.** Ghi minimum C++ standard, compiler versions, standard library features bắt buộc và những tính năng chỉ được bật ở một số toolchain.

Ví dụ, một thư viện giữ C++17 làm baseline có thể đặt tiện ích C++20 trong target hoặc module riêng nếu ranh giới API cho phép. Nếu kiểu C++20 xuất hiện trong header công khai, mọi người dùng header đó cũng phải đáp ứng yêu cầu chuẩn tương ứng.

Với API dùng `std::expected<int, Error>` để chia số nguyên, hợp đồng phải xác định riêng chia cho 0 và tràn số có dấu (ví dụ giá trị nhỏ nhất chia cho `-1`). Trả lỗi có kiểu không làm phép toán tràn trở nên hợp lệ; hàm cần phát hiện điều kiện đó trước khi thực hiện phép chia.

## 28. Tổng kết kiến thức

| Phiên bản | Những điểm quan trọng |
|---|---|
| C++17 | Structured bindings, `if constexpr`, optional, variant, filesystem |
| C++20 | Concepts, Ranges, Coroutines, Modules, span, format, jthread |
| C++23 | expected, print, mdspan, generator, Ranges improvements, explicit object parameter |

C++17 cung cấp nền tảng phù hợp cho nhiều ứng dụng và thư viện phổ biến. C++20 mở rộng đáng kể generic programming, ranges, concurrency và cách tổ chức chương trình; C++23 bổ sung thêm API như `std::expected`, `std::print` và `std::mdspan`.

Khả năng chọn một chế độ chuẩn không chứng minh compiler và standard library đã triển khai mọi tính năng của chế độ đó. Feature-test macros, compile tests và CI trên toolchain mục tiêu giúp xác định phần nào thật sự dùng được.

Nâng chuẩn có thể ảnh hưởng source compatibility, ABI, dependency và build infrastructure. Vì vậy, chọn chuẩn theo nhu cầu và nền tảng triển khai; tính năng mới chỉ đáng đưa vào khi lợi ích về biểu đạt, an toàn hoặc bảo trì bù được chi phí tương thích.

**Nguyên tắc quan trọng nhất:** Sử dụng tính năng mới khi nó giải quyết được vấn đề thực tế, không phải chỉ vì phiên bản mới có cung cấp tính năng đó.

Một codebase sử dụng C++17 đúng cách vẫn có thể dễ bảo trì hơn một codebase C++23 sử dụng quá nhiều kỹ thuật không cần thiết.

Ngược lại, những dự án thực sự hưởng lợi từ Concepts, Ranges hoặc `std::expected` cũng không nên bị giữ lại ở C++17 chỉ vì thói quen.

Mục tiêu là xây dựng phần mềm đúng đắn, ổn định, có khả năng mở rộng và phù hợp với vòng đời của sản phẩm.
